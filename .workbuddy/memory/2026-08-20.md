### Phase 3 实现内容（代码完成，未能提交）

新增 migration **v82** `syncChangesV2Migration.ts`（name `sync-v2-change-feed`）：
- `sync_changes_v2` 通用 Change Feed，覆盖全部六类实体，sequence 单调递增；

- 12 个 `sync_v2_*` 触发器，全部带 `WHEN ... workspaceId IS NULL AND
  (SELECT enabled FROM sync_v2_should_log) = 1`。

新增 `backend/src/sync/suppression.ts`：
桥接 Node 侧与 SQLite 触发器。**触发器读不到 AsyncLocalStorage**，
所以必须用库内开关表；计数式嵌套 + finally 复位 + 启动时
`resetChangeFeedSuppression()` 兜底（上次运行在抑制窗口内被强杀会卡在 1，
导致此后所有写入都不进 feed，等于同步永久静默失效）。

新增 `backend/src/sync/apply.ts`：服务端 mutation 应用层，六类实体各自的
upsert/delete。关键决策：
- note 是唯一带版本冲突检测的实体（它承载正文）。**已存在的笔记若缺少
  baseVersion 一律判冲突**，不盲目覆盖；
- notebook 的 delete 走软删（isDeleted=1），硬删会级联清掉其中笔记；
- note_tag / favorite 用复合 entityId（`noteId:tagId` / `userId:noteId`），
  并校验笔记归属，防止越权挂标签；
- attachment **只同步元数据且不接受 upsert 创建**——二进制必须先通过上传接口
  落地，否则元数据会指向不存在的文件。

新增 `backend/src/routes/sync-v2.ts`，挂载 `/api/sync/v2`：
plan / changes / snapshot / push / ack。
- Flag 关闭时全部端点返回 404 `SYNC_V2_DISABLED`，不存在半启用状态；
- 第一版**显式拒绝** workspaceId（`SYNC_V2_SCOPE_UNSUPPORTED`），
  而不是静默按个人空间处理——否则客户端会误以为工作区已同步；
- **push 的每条 mutation 独立成事务**：一条冲突不回滚同批次其他条目，
  否则客户端只能整批重试，永远卡在同一条坏数据上；
- 冲突时回传 serverVersion，供客户端构造三方冲突记录；
- changes 未满页时把 nextSequence 推到 serverSequence，
  避免客户端因"他人产生的序号"反复空转拉取；
- snapshot 按固定实体顺序 notebook→tag→note→note_tag→favorite→attachment
  分页，父实体先于子实体，游标为 `entityType:id`；附件不回传服务器 path。

`/api/offline-sync` 与 `offline_sync_changes` 一个字未改，V1 触发器完整保留。

### Phase 4 完成（Desktop Sync Engine）

新增 4 个文件，**无新增 migration**（复用 v81/v82 的表）：

`backend/src/sync/remote.ts` — Sync V2 远端客户端
错误分类是核心职责，Engine 据此决定重试/暂停/冲突：
网络异常与 AbortError → NETWORK_UNAVAILABLE（重试）；401/403 → AUTH_EXPIRED
（暂停，重试无意义）；5xx 与 **404** → SERVER_ERROR（404 意味着远端未启用 V2，
不能误判为"数据不存在"）；其他 4xx → INVALID_PAYLOAD。
`FetchLike` 允许注入，测试不打真实网络。

`backend/src/sync/push.ts` — Mutation Coalescing
update+update→最新；create+update→create with latest；update+delete→delete。
**关键取舍：baseVersion 取最早那条**——冲突检测问的是"这串修改基于服务端哪个
版本开始"，取最新会让本地连续编辑自己跟自己比，从而漏判与远端的真实冲突。
被合并条目的 mutationId 记入 `supersededIds`，推送成功后一并出队，
否则它们会永远留在 Outbox 反复重试。
合并后保持"实体首次出现顺序"，notebook 仍先于其 note。

`backend/src/sync/applyLocal.ts` — 远端变更写入本地
**必须双层抑制**：`runWithOutboxSuppressed`（Node 侧 enqueue）+
`runChangeFeedSuppressed`（SQLite 触发器读不到 Node 上下文）。只抑制一层会漏。
若实体在 Outbox 里还有待推送 mutation（`hasPendingLocalChange`），
远端版本**不覆盖**，转入 pendingConflicts —— 那是用户尚未上传的内容（RULE 3）。
关系型实体父实体缺失时跳过（下轮 Pull 会重带），硬插会违反外键。
附件 path 写占位 `pending-sync:<id>`，远端不会也不应回传服务器路径。

`backend/src/sync/engine.ts` — 状态机与编排
一轮固定 Push → Pull → Apply → ACK（先推后拉，本地内容不会被自己的旧版本覆盖）。
Change Feed 只给"哪些实体变了"，完整内容通过 snapshot 单点拉取并提前终止
（`wanted.size === 0` 即 break），避免协议在 feed 里塞正文。

### Phase 4 修掉的两个真实缺陷（实现过程中由测试暴露）

1. **`state === "disabled"` 被用作"未启动"的判定**，导致手动触发
   `syncOnce()` 必须先 `start()`，很容易漏调而表现为"点了没反应"。
   改为引入独立的 `stopped` 字段：state 是"同步健康度"（随网络/授权变化），
   stopped 是"用户意图"（只有 start() 能清除）。二者混用会让一次网络故障
   把引擎永久关停。`scheduleNext` 也加了 stopped 检查，避免 stop 后残留定时器唤醒。

2. **断网后条目永久卡在 inflight**（严重）。Push 前标记 inflight，
   但 `client.push()` 抛异常后没有复位，该条目在本次进程内再也不会被
   `listPendingMutations` 取出——网络恢复也不会重传，只有重启进程才恢复。
   修复：push 失败时 `recoverInflightMutations()` 退回 pending 再 rethrow；
   同时在正常响应处理后也兜底复位一次，覆盖"服务端漏回某些 mutation 结果"
   的部分响应场景。重复推送由 mutationId 幂等保证安全。
   已加专门回归测试锁死此行为。
