# 目录父级丢失后经同步传播：回归验证

## 问题与原因

桌面端首次下载后，部分子目录出现在根级；随后同步，服务端及其它副本也出现相同层级变化。

已发布的 v1.5.5 在 `backend/src/sync/applyLocal.ts` 应用目录时，仅检查父目录是否已经存在于本机。快照按 UUID 排序，子目录可能先于父目录到达或与父目录分处不同页；本机将尚未到达的父目录当作空父级写入，后续父目录到达也不补回链接。

目录更新的 Outbox 触发器保存完整快照，包括 `parentId`。仅展开或折叠目录也会上传当前父级，因此下载时产生的空父级能够继续传播。这个缺陷已通过合成数据复现；支持日志没有逐目录的旧/新父级，不能据此断言全部历史异常的来源，也不能用日志自动恢复全库。

## v1.6.0 的覆盖

`release/v1.6.0` 在本次新增回归前已包含 `f21d8b648` 的运行时修复：目录按依赖落库、首次下载跨页收齐目录段、游标保护、已删除子树及隐藏根文档容器的父子链保留、未上传移动的冲突保护，以及不可重试结构故障的脱敏诊断。

本次补充传播链回归及 DCC-005 映射，保留该分支后续已有功能和修复。

## 回归场景

用例：`DCC-005: child-first downloads followed by folder expansion never flatten the desktop, NAS or second device`。

测试通过真实 SQLite 和 Sync V2 路由使用合成数据：1 个父目录、9 个子目录、9 篇笔记。将快照目录重新排成旧服务端的 UUID 顺序，使 5 个子目录先于父目录到达，验证新客户端仍兼容旧服务端。

下载后只折叠目录，不执行移动。分别检查首次下载结果、Outbox 中每个目录的父级、服务端、第二个副本及三份知识树投影，同时检查笔记归属。目录计数相同或队列清空均不作为层级完整的替代证据。

- 未修复的 v1.5.5：用例按预期失败，5 个子目录落到根级，空父级进入队列并传到服务端及第二副本。
- v1.6.0：相关后端 9 个测试文件共 169/169 通过，桌面下载门禁 16/16 通过；数据一致性契约映射检查通过 12 项不变量、343 项测试引用。映射检查不代替行为测试。

自动化使用进程内 HTTP 适配器调用真实 Sync V2 路由；不代表 Windows 安装包、真实网络或生产数据恢复已验收。后端测试使用 Electron 的 Node 模式以匹配已有 better-sqlite3 ABI，并以 `--test-force-exit` 结束已有开放句柄。

## 已损坏层级的恢复边界

修复避免这条下载路径再次产生错误层级，不自动猜测已有目录的原始父级。恢复前应暂停旧客户端同步，备份当前数据库、附件、Outbox 和冲突记录；运行中的 SQLite 应通过一致性备份获取副本，不能遗漏 WAL。

可用异常前备份或独立正常副本核对稳定目录 ID。没有旧备份时，应只读检查历史基线冲突的 `remotePayload` 是否仍保留原始父级，再生成逐项恢复预览。检查、预览和后续恢复都不能清空未确认队列或丢弃冲突双方。

恢复验收需要比较目录 ID、父子链、笔记归属及正文/附件完整性，并由第二设备实际拉取确认。本次没有操作用户生产数据，也未发布安装包。
