## 第二轮复核：结论继续维持 NO-GO

这次 AI 的工作比第一轮扎实：它重新核对了失败项、区分了真实缺陷与过时测试，并补充了数据库触发器及文件沙箱的验证。

我刚刚再次核对 GitHub，当前 `release/v1.5.2` 的 HEAD 确实是 `99dbdef9`。但有两个判断需要保留谨慎：

1\. BUG-02（永久删除）并没有因为触发器正常工作而消除风险。

触发器可以保证删除后的知识树和同步记录一致，却不能让已经永久删除的正文、历史记录及附件恢复。

源码中的 `permanentlyDeleteNote()` 没有显式检查 `isTrashed = 1`，而旧 `DELETE /api/notes/:id` 直接调用它。这是可确认的危险 API 语义；即使正常 UI 使用软删除，也不应该忽略。

2\. BUG-06（Plugin Studio 硬链接）确实存在保护缺口，但是否属于可远程利用的安全漏洞，还要看攻击者能否创建硬链接。

`projectPaths.ts` 逐层检查了符号链接，却没有拒绝硬链接。`projectService.ts` 随后直接读取解析后的文件路径，因此第二轮描述的读取行为与源码相符。

不过，报告中的硬链接实验是在测试代码主动调用 `fs.linkSync()` 后进行的。它证明文件系统层面的隔离缺口，尚未证明普通远程用户仅靠 Plugin Studio API 就能创建这种链接。

所以我的判断是：BUG-06 至少需要修复和补测试，但安全等级应依据真实攻击前提确定，不能直接宣称远程文件读取漏洞。

## 一个需要纠正的重要发现：BUG-02 的影响范围比报告描述更大

进一步检查后，发现旧版永久删除接口不只是一个没人使用的历史入口。

目前仍有实际调用方：

| 调用方                                                    | 当前实现                            |
| ------------------------------------------------------ | ------------------------------- |
| `packages/nowen-sdk/src/client.ts`                     | `deleteNote()` 直接调用永久删除 API     |
| `packages/nowen-mcp/src/api-client.ts`                 | `deleteNote()` 调用相同接口           |
| `packages/nowen-mcp/src/index.ts`                      | 通过 `permanent` 参数区分永久删除与软删除     |
| `frontend/src/lib/api.impl.ts`                         | 仍然暴露 `api.deleteNote()`         |
| `frontend/src/components/AndroidShareImportCenter.tsx` | 部分导入失败清理流程使用 `api.deleteNote()` |

这意味着它不是完全废弃的 API，而是仍然承担真实业务功能。

我会把 BUG-02 的建议等级从报告的 P2 提升为 P1 候选，原因不是 ACL 越权，而是：在一个已经推广回收站和数据恢复体验的笔记软件中，通用删除接口仍具备不可恢复的永久删除语义。

建议在现有调用方完成兼容性审查后，明确区分“移入回收站”与“永久删除”，并阻止普通有效笔记意外进入永久删除流程。不能简单删除旧接口，否则可能影响 SDK、MCP 和导入失败清理。

有三个技术细节尤其重要：

- BUG-02： SDK 明确提供 `trashNote()` 和标注为永久删除的 `deleteNote()`，MCP 的 `permanent` 默认也是 `false`。说明永久删除部分属于有意设计，不宜简单删除接口。真正要评估的是，是否必须先进入回收站、是否需要单独的永久删除端点与确认机制。
- BUG-06： 不能只增加 `stat.nlink > 1` 就宣称文件沙箱完全安全。还应核查文件路径检查与实际打开之间的竞态、项目目录写入权限，以及远程 API 能否构造利用条件。
- E2E 导出： `state=ready` 和 `downloadToken` 只能证明产物准备好，仍应实际下载并校验内容完整性。
