## 八、缺陷分级和发版标准

P0：数据丢失、数据损坏、权限绕过、加密泄露、无法启动、无法恢复或核心同步破坏。

P1：核心功能不可用、严重跨端不一致、关键业务无法完成、可稳定复现的严重崩溃。

P2：一般功能异常、有可接受替代操作的交互问题。

P3：轻微视觉、文案或低影响问题。

发版要求：

- P0：0 个未解决。
- P1：0 个未解决；例外必须由维护者明确批准。
- 核心数据安全与同步测试：全部通过，未测试不得冒充通过。
- 高风险已修复 Bug：必须回归。
- 关键构建及测试门禁：通过。
- 真机/跨平台未测试项：明确标注发布风险。
- 不符合要求时输出 NO-GO，不要迎合发版目标。

## 四、怎么执行效果最好？

最推荐使用有本地代码仓库、终端、浏览器自动化和 Android 测试环境的 AI 开发工具。只连接 GitHub 的 AI 可以做源码审计、测试用例设计、检查 CI 和提交自动化测试代码，但不能凭 GitHub 连接就宣称完成了真实客户端测试。

我建议第一轮先执行上面的完整提示词，只发现和记录 Bug，不同步大规模修业务代码。随后再按 P0 → P1 的顺序逐项修复并验证，避免一边测试一边改动导致最终基准不断变化。

长期最值得投入的能力是把这套回归体系固化在 Nowen Note 仓库中：以后每次发版，只需触发一次 Full Regression 流程，就能自动生成覆盖率、失败用例、历史 Bug 复测结果和 GO / NO-GO 发版报告。
