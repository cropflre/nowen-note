# Nowen Note 数据一致性契约（Data Consistency Contract）

> 状态：v1（2026-10-10）。适用范围：笔记与知识树相关写入、离线修改、Sync V2、Android Native SQLite、桌面端内嵌后端 SQLite、Web 离线队列以及备份恢复。
>
> **本文件是用户数据安全的工程约束，不是“所有设备永不丢数据”的保证。** 当前已覆盖的自动化用例参见 [机器可读测试矩阵](./data-consistency-contract.matrix.json)；自动化测试无法替代真实设备、断电、存储空间不足和生产备份恢复演练。

## 0. 产品承诺与术语（必须区分）

| 状态 | 唯一允许的技术含义 | 不得推断 |
| --- | --- | --- |
| 正在保存 | 当前持久化操作尚未成功返回；编辑器中的临时内容可能仅在内存中 | 已写入本地数据库 |
| 已保存到本机 | 对该编辑的本地持久化事务已完成（或明确受限于当前浏览器持久化能力） | 服务器已收到 |
| 等待云端同步 | 修改已经进入当前设备可恢复的 Outbox / 离线队列，尚无服务端确认 | 其他设备已经可见 |
| 云端已确认 | 服务端已持久化并认可**对应的 mutation/版本**，而非仅 HTTP 请求发出 | Android/其他设备已拉取或附件已完成下载 |
| 冲突待处理 | 同一实体的本机意图与服务端版本无法安全自动协调，待用户选择或显式规则处理 | 任意一侧应被自动抛弃 |
| 同步异常 / 需要登录 | 上行或下行失败，可能含待处理写入或旧快照 | 本地数据无效、应清除客户端 |

**严禁将“HTTP 200”、“本地缓存命中”、“队列入队成功”、“已发送”或“最后同步时间更新”单独作为笔记版本已云端确认的依据。** 收到服务器 applied / duplicate ACK 也只代表服务器确认该 mutation，并不证明其他设备已可读。

## 1. 平台的权威数据源边界

| 平台 / 运行模式 | 写入与恢复边界 | 注意事项 |
| --- | --- | --- |
| Windows/macOS 桌面安装版（内嵌后端） | 本地后端 SQLite 提交；同步启用时由 Outbox 驱动 Sync V2 | 关闭客户端、暂时断网均不等于已上传云端 |
| Android/iOS Native Local-first | 设备 Native SQLite + Native 附件存储；Sync V2 后台拉取、推送 | 必须先区分仅本机与已绑定服务器账号，绝不跨账号上传旧队列 |
| Web 连接服务端 | **Remote-first + IndexedDB/浏览器离线缓存与队列**，不同于 Native SQLite | 浏览器清数据、隐身模式、配额耗尽会影响本地副本；不能承诺与桌面端相同的离线持久性 |
| 多端同步（含节点小宝代理） | 服务端持久化 ACK 与客户端接收/应用/本地游标确认是多个阶段 | 代理返回登录页、401、非法 JSON 或未知协议实体均不能假装同步成功 |
| 全量备份 | SQLite 数据库 + 实际受管附件/文件与元数据，经校验方可恢复 | 云端同步不是备份，单份备份也不是恢复成功的证明 |

## 2. 不变量（版本 v1）

每条编号都绑定了 CI 运行的具体真实测试文件及测试用例。修改对应代码时必须保持相关测试通过；增强协议时应先补失败复现、再改实现。

- **DCC-001 — 云端确认必须可证明。** 需要服务端版本推进或针对 mutation 的 applied / duplicate 确认才能清除待同步标记。只发生本地写入或 API 请求失败，不允许展示“云端已确认”。
- **DCC-002 — 本地持久化和待同步意图。** 同步启用时实际业务 CRUD 必须产生正确的 Outbox mutation（含 baseVersion、scope/Profile），且本地修改可在应用重新初始化后恢复；禁止“界面显示保存成功，但写入或出队根本未提交”。
- **DCC-003 — 失败不得静默出队。** 断网、5xx、超时、暂停同步、异常退出等路径须保留本地数据与可恢复的待发送意图；retryCount / 错误状态不应伪装成成功。
- **DCC-004 — 冲突双方不可悄悄丢弃。** VERSION_CONFLICT 必须保留可追踪的本地版本与服务器版本；不得用一次普通拉取覆盖尚未发出的编辑；合并和选择版本须有可解释的操作及回滚/历史边界。
- **DCC-005 — 游标/ACK 不能先于数据有效性与落库。** 未识别实体、丢失正文快照、失败的反序列化或数据库事务都必须阻止推进拉取游标；不能通过 ACK 略过尚未可靠应用的数据。
- **DCC-006 — 账号/Profile/服务器作用域隔离。** 新账号/新服务器不能继承其他账号的未发送写入；切换账号、令牌更新不能更改 Outbox 的归属。
- **DCC-007 — 删除是显式操作。** 用户明确删除才发出 delete mutation/墓碑；“下载不到”“权限失败”“返回 404”“快照缺一条”不能自动推断为用户的删除意图。
- **DCC-008 — 备份恢复必须先校验、失败要保护原数据。** 附件和数据库快照校验失败时不得覆盖正在使用的数据；发生中途失败，原数据库及受管文件应有回滚/保护路径。
- **DCC-009 — Native 离线与身份安全。** Native 仅此设备模式的编辑在重启/初始化后仍保留；重新连接服务器前不能偷发写入；同步成功后方可清除相应待发送 mutation。
- **DCC-010 — Web 离线并不是云端确认。** Web 端失败写入、冲突快照必须保留在已有浏览器队列/冲突存储中，不能把“排队中”渲染成“服务器最新”；浏览器离线存储的实际耐久性仍受浏览器环境限制。

## 3. 关键时序约束

### A. 本地写入
`编辑请求 → 本地事务提交（含同步意图） → 允许显示“已保存到本机” → 后台推送 → 服务端确认对应 mutation / 版本 → 允许显示“云端已确认”`。

如果本地提交失败，要明确显示失败并允许重试/恢复草稿；任何成功 UI 均不能由组件乐观更新本身触发。**当前产品各编辑器尚未统一接入“同步收据”UI**（见第 5 节），这里规定的是后续实现必须遵守的条件。

### B. 断网与恢复
`网络故障 → 本地修改保留 + 记录失败 → 可重试（退避/登录重验） → 使用原 mutationId 幂等重推 → 只有 ACK 对应的项出队`。不得清空整个队列、猜测服务端状态或把所有待同步项标记已完成。

### C. 拉取和冲突
`拉取变更标识 → 获取完整快照 → 类型/权限/加密格式校验 → 本地事务应用或登记冲突 → 持久化游标 → 远端 ACK`。某一步不成功，则下一轮从安全位置重试。知识树结构缺失时不得强行合并；应诊断父节点/业务资源是否完整。

### D. 删除与备份
删除使用用户可追溯的显式意图、版本检查和墓碑；恢复使用完整性审计与可恢复的临时阶段。**禁止为了“消掉冲突”删除全部本地缓存、重新建库或清空 Outbox**，除非用户清楚理解后果、完成备份并确认操作。

## 4. 可执行测试门禁

测试矩阵：`docs/architecture/data-consistency-contract.matrix.json`。每个 DCC-xxx 对应一个或多个真实自动化测试用例。检查脚本除运行实际测试外，还校验**契约编号、用例文件和用例名称保持对应**，防止重构时测试被删除、CI 却继续绿灯。

```bash
# 在仓库根目录执行
node scripts/data-consistency-contract.mjs --verify

# 第一次运行前分别在 backend、frontend 执行 npm ci
node scripts/data-consistency-contract.mjs --backend
node scripts/data-consistency-contract.mjs --frontend
```

GitHub Actions：`.github/workflows/data-consistency-contract-ci.yml`，对同步、离线、账号隔离、备份恢复相关路径的推送/PR 启动以上检查。**仓库管理员仍需在 Settings → Branch protection / Rulesets 将 `Data Consistency Contract` 相关检查设为 required，才会成为不能绕过的合并门禁。** 仓库权限与分支保护由管理员掌控，单独添加 CI 文件不会自动开启强制审核。

### PR 评审核对

涉及笔记、表格、知识树、附件、移动端 Native、本地缓存、同步、账号或备份的变更，至少回答：

1. 哪一份数据是当前权威源？哪个事务才算本地已保存？是否会遗失草稿？
2. 断网、401/403、500、超时和进程重启时，旧数据/Outbox 如何保留？
3. ACK、冲突、错误/重试以及下行游标何时更新？能否跨账号串队列？
4. 删除、备份恢复、数据库迁移是否需要预备快照和失败回滚？
5. 改动对应哪些 DCC 编号，新增或更新了哪些失败回归测试？

## 5. 已具备的保障与尚未完成的工作（不可混淆）

**已具备相关回归覆盖：** Sync V2 Outbox CRUD/失败重试/服务器 ACK/版本冲突/游标保护、Web 队列失败留存、Native SQLite 断开与恢复、跨身份隔离、备份完整性和故障回滚。测试覆盖范围见矩阵；它只能证明给定测试场景，不能声称任意意外断电或磁盘故障绝不会丢失数据。

**尚未统一实现，后续应另开 Issue/PR：**

- 为所有编辑器和轻量表格统一 `localRevision / acknowledgedRevision / conflict` 的**同步收据**（Sync Receipt）与原子状态更新；不要先造假的“已同步”标签。
- 基于该收据统一「正在保存 / 已保存到本机 / 等待云端 / 云端已确认 / 冲突 / 失败」文案，区分服务器持久化与其他设备应用完毕。
- Native Android/iOS、桌面与 Web 的真实设备断网、切账号、重启、强杀、磁盘不足、代理异常、附件一致性全链路验收。
- 备份/恢复在 SQLite 与 PostgreSQL、对象存储等部署组合下的生产级恢复演练和附件逐项校验报告。

契约更新规则：先扩充测试矩阵和失败用例，再实施行为变更，最后更新文档中的覆盖状态。未经验证，不得把“待实现”的保证标成已交付。
