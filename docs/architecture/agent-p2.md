# Agent P2 implementation contract

Baseline: `ccb139cb`, isolated branch `codex/ai-agent-p2`, 2026-10-24. The maintainer explicitly requested P2 while the earlier real-model/device gates remain open. The running P1 workspace and its database are preserved.

## Implementation plan and acceptance

1. Migration 138 adds owner-scoped templates, MCP connections and durable tool-call receipts. Templates include fixed notebook scope, instruction, locale/timezone, allowed note/task actions and explicit extension grants. Existing personal Prompt templates can be copied, never implicitly granted tools. Acceptance: CRUD isolation, stale/revoked grants, migration idempotence.
2. Reuse Automation schedules/events/signed webhooks with one `agent` step referencing a template. Triggers create proposals only. Persist the mapping from automation run to Agent run atomically, reject cross-scope/depth loops, and never re-execute an interrupted run. Acceptance: schedule/event/webhook deduplication, cancellation/restart, no writes before approval.
3. Plugin actions use the existing plugin service, restricted to enabled official/verified sandbox-js plugins; local Node actions are excluded. MCP uses a separately configured public HTTPS endpoint, explicit tool allowlist, encrypted bearer credential and DNS-pinned existing secure transport. No shell, arbitrary URL tool, local/private target or redirects. External actions execute only after the exact parameters and destination are approved; uncertain remote outcomes cannot be blindly retried. Acceptance: allowlist/revision checks, SSRF/timeout/size limits, no credentials/bodies in Agent audit metadata, duplicate approval and lost response behavior.
4. Add template, permission, connection and recurring-task UI within the Agent panel, with zh/en coverage. Reuse P1 preview/history/navigation. Acceptance: template → scheduled proposal → approval → persisted result, plus P0/P1 regression and builds.

Expected files: `backend/src/agent/{templates,extensions,mcpClient,p2Routes}.ts`, migration 138 (SQLite/PostgreSQL), bounded additions to workflow runtime/schemas and Automation validator/runner, `frontend/src/components/agent/AgentTemplates.tsx`, API/types/locales, tests and API/user/QA documentation. Server configuration is not propagated by Sync V2; created notes/tasks retain existing transactional Outbox behavior (DCC-002/006). External remote side effects cannot be committed atomically with SQLite; receipts must distinguish attempted/confirmed/uncertain.

Protocol sources: official [Streamable HTTP 2026-07-28](https://github.com/modelcontextprotocol/modelcontextprotocol/blob/main/docs/specification/2026-07-28/basic/transports/streamable-http.mdx) and [tools](https://github.com/modelcontextprotocol/modelcontextprotocol/blob/main/docs/specification/2026-07-28/server/tools.mdx). Compatibility limitations and exact local acceptance results will be documented with implementation.

## Implemented boundaries

Migration 138 creates `agent_templates`, `agent_mcp_connections`, `agent_extension_receipts` and `agent_trigger_runs`; existing business tables and synchronization formats are unchanged. PostgreSQL SQL supplies metadata parity, not a PostgreSQL Agent runtime. Templates and connection configuration belong to one user; templates additionally bind the exact personal/workspace scope. Prompt import copies only the current user's `ai_custom_prompts` text and starts with no write/tool grants. Templates are revision checked on every run/tool/approval. A model cannot change the stored instruction, notebook, language, timezone or allowed capabilities by forging the create request.

Agent Automation definitions contain exactly one `agent` step with `templateId` and `templateRevision`. They use the existing durable schedules, event ledger, four-worker dispatcher and signed webhook service. New plans are disabled until explicitly enabled. Updating a template invalidates the old plan revision; create a replacement plan and pause/delete the old one. Manual trigger requests, scheduler occurrences and webhook deliveries map to an Agent run through `agent_trigger_runs`, in the same transaction as run creation; execution begins in a microtask after commit. Repeated delivery returns the existing run ID. Cancellation/enabled state are read again immediately before dispatch. A restarted automation run is never silently re-executed.

Events must match the template owner and workspace. Note events must also belong to the chosen notebook/descendant scope. Sync/plugin/workflow sources and nonzero depth cannot trigger Agent recursively. Event and webhook payloads are not interpolated into prompts. An event merely requests the saved template; it cannot override permissions or inject instructions. The normal AI switch, account status, notebook ACL, protected-content exclusions and per-user active-run limit apply to all triggers.

The model can propose up to three `extensionCalls` from the template's explicit tool catalog. Every proposed call includes its exact destination and arguments in the review. Calls execute **after** approval and after approved local note/task transactions. No external result is fabricated before execution. Results are displayed as escaped text for human review; they are not automatically fed into a second model loop or used to perform follow-up writes. For external calls a durable `attempted` receipt is committed before sending; confirmation changes it to `confirmed`. Lost/invalid/oversized responses yield `uncertain`, keep completed local resources, and prohibit retry. Completed calls are skipped. Receipts store only tool IDs, status, argument digests and time; output remains in bounded process memory.

Plugin actions reuse PluginService and QuickJS, including its existing signature/policy/lifecycle and input validation. Agent additionally permits only enabled `official`/`verified` sandbox plugins whose declared permissions are empty or limited to their own plugin storage. Community/developer plugins, Node actions, library-wide resource access, network and credential privileges are not exposed. Trust/manifest/checksum changes revoke an in-flight grant. This deliberately excludes powerful existing plugins until a separate resource-scoped broker design exists; verified is not treated as a universal sandbox guarantee.

MCP is a stateless **2026-07-28 Streamable HTTP** client. It supports `tools/list`, `tools/call`, bounded JSON and request-scoped SSE, standard request metadata and safe primitive header annotations. Unsupported protocol versions, server-initiated requests, input-required results, invalid schemas and incomplete responses fail closed. There is no legacy initialize/session transport, stdio/process launch, OAuth browser flow, sampling, elicitation or arbitrary server callback. An optional bearer token uses existing AES-GCM secret storage. Credentials cannot appear in URLs/query strings, logs, tool catalogs or model context. Server responses echoing a credential are rejected during discovery or redacted from displayed results.

The existing secure external fetcher validates and pins public DNS answers, checks CNAME/IP ranges, enforces HTTPS/exact-host authorization, rejects redirects and uses no general AI proxy. Budgets are 15 seconds and 128 KB per MCP response, 16,000 characters for proposed parameters, 24,000 characters per displayed result, 12 grants/template, 50 templates/user and 20 connections/user. Tool discovery requires a separate explicit action and retains only named allowlisted tools; refreshing a changed catalog invalidates prior grants. No remote schema URL is fetched. MCP schema declarations remain untrusted; the target server validates its complete input schema in addition to local bounded object/annotation checks.

Backup restore clears MCP credentials and discovered tools alongside existing Automation quarantine. A running external request cannot be rolled back or reliably cancelled; Stop prevents subsequent calls and exposes the durable receipt for inspection. The original ten-minute run/draft lifetime remains: scheduled proposals require timely review while the server is online, expire on restart, and are never silently approved. This release does not promise unattended writing or durable generated summaries after expiry. Template instructions are deliberately saved configuration, distinct from generated note bodies and ephemeral previews.

No new global queue, task generator, plugin worker system or MCP subprocess is introduced. See [API](../api/agent-p2.md), [user guide](../user/agent-p2.md) and [QA](../qa/agent-p2-2026-10-24.md). Issue linkage remains the supplied V1 task brief; no new public issue/comment/status changes were made.
