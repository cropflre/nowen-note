## 3. 发布流程唯一化

**正式入口（唯一）**

1. `release-build.yml`（`workflow_dispatch`，Node 24.22.1）— 按 `targets` 构建候选产物，产出不可变 manifest
2. `release-publish.yml`（`workflow_dispatch`，Node 24.22.1）— 校验同 SHA/Tag、`environment: release-github` / `release-docker` 审批门禁、需重输版本号确认，才发布 GitHub Release 与 Docker

**已封堵的并行路径**

| 工作流 | 现状 |
| --- | --- |
| `publish.yml` | `Legacy Publish Disabled`，仅 `workflow_dispatch`，执行即 `exit 1` |
| `release.yml` | 移除 tag push 触发；`release-assets` 需 `NOWEN_LEGACY_RELEASE_ASSETS_ENABLED=1`；`--publish never` |
| tag 推送 | 全仓库已无 `on.push.tags` 的构建/发布工作流（仅 `extension-ecosystem-rc1-ci.yml` 保留 tag 语义校验） |

**Node 24 兼容性**：`release.yml`、`release-build.yml`、`release-publish.yml`、`release-center-*.yml`、`ios-release.yml`、`microsoft-store-appx.yml`、`studio-production-docker-rc.yml`、`windows-direct-release-ci.yml` 全部为 `24.22.1`；`publish.yml` 因已是占位文件不含 Node 配置。

**本轮修复**：`frontend-loading-performance-ci.yml` 与 `asset-ai-ci.yml` 原先在 `npm ci` 之后又用 `--no-save` 把 `@playwright/test` 覆盖成 `1.48.2`，在 2026 的 ubuntu runner 镜像上浏览器与 `--with-deps` 系统依赖已无法安装（Frontend Loading Performance CI 稳定失败于此）。改为复用 lock 中的 `1.63.0`。

## 5. 尚未解决的高风险问题

1. **Docker 升级 RC 持续失败**（P0，阻塞发布）：v1.5.3 数据卷升级到 v1.5.4 的端到端验证在 CI 上连续两次失败（10-30 11:16、13:00），本地无法复现。用户升级 Docker 是主要路径，此项未过不能发布。
2. **Release Center CI browser contracts 失败**（P1）：不进入安装包，但属于发布控制台的验收门禁。
3. **后端测试无全量 CI**（P1）：CI 按功能切片，386 个后端测试文件只有一部分被专项工作流覆盖；`docker-hardened-entrypoint`、`docker-updater-jobs` **完全无 CI 覆盖**，本机 Windows 亦无法运行（前者需 POSIX bash，后者 Windows 不能监听 Unix socket）。建议补一个 ubuntu 上的 `npm test` 全量 job。
4. **产品叙事分歧**（P2）：`main` 主张把 Studio/V3 归入 v1.6.0，`release/v1.5.4` 的 README 与 CHANGELOG 记在 v1.5.3。合并 main 前必须由产品负责人裁决，否则对外文档与已交付功能矛盾。
5. **本机 Node 版本偏离**（P2）：默认 `node` 为 22.22.2 / 20.20.2，项目要求 `>=24.22.1`，本地跑测试会因 jsdom Blob 跨 realm 等差异产生假失败。已在本机安装 24.22.1 规避。
