# 笔记附件目录归属关系修复设计

## 问题

`GET /api/files?noteId=<id>` 当前仅通过 `attachment_references` 查询正文中出现过附件 URL 的记录。附件表自身的 `attachments.noteId` 表示附件首次归属的笔记，但该条件没有进入查询，导致空白笔记已经拥有附件时，附件目录仍显示 0。

## 目标

- 附件首次归属于当前笔记时，即使正文尚未包含附件 URL，也应出现在该笔记的附件目录中。
- 当前笔记引用其他笔记上传的附件时，继续通过 `attachment_references` 展示。
- 不自动修改或回填笔记正文，不改变“正文引用”“未引用附件”等既有语义。

## 方案

只调整 `/api/files` 的 `noteId` 筛选条件：附件满足 `attachments.noteId = noteId`，或在 `attachment_references` 中存在该笔记的引用记录时返回。前端继续消费同一接口，不增加合并请求或特殊兜底。

文件详情中的“引用此文件的笔记”仍只展示真实正文引用；`primaryNote` 继续单独表示首次归属笔记，避免把归属关系误写成正文引用。

## 测试

在现有附件路由测试中创建正文为空的笔记并上传附件，确认：

1. 修复前 `GET /files?noteId=<id>` 不返回该附件，回归测试能够稳定失败。
2. 修复后接口返回该附件，数量和附件 ID 正确。
3. 现有文件列表、签名访问地址和跨笔记正文引用行为不受影响。
