# 思源导入性能与进度稳定性设计

## 目标

1. 消除思源数据包中 `.sy` 文档被重复解压、重复 JSON 解析的性能回退。
2. 降低批量写入笔记时统一知识树同步产生的重复数据库查询与递归校验。
3. 让用户看到真实的导入阶段和处理数量，不再把转换、附件处理、写入等全部显示为“正在解析”。
4. 导入期间始终只展示一个稳定的进度状态，轮询更新不得造成双卡、上下跳动或重复入场动画。
5. 保留现有后台任务的幂等领取、心跳、断线恢复、超时和终态停止规则，避免重复导入。

## 已确认根因

### 数据包被读取两遍

`siyuanPackageImport.ts` 的增强包装层会先打开 ZIP，遍历全部条目并解压、解析每个 `.sy` 文档，以读取目录顺序、图标和保真节点。随后 `siyuanPackageImportLegacyCore.ts` 再次打开同一个 ZIP，并再次解压、解析全部 `.sy` 文档后才开始转换与写入。

数据包中文档数量和正文体积增加时，重复的解压、字符串创建、JSON 解析和 AST 常驻会直接拉长任务前半段耗时并放大内存峰值。

### 逐篇知识树同步重复读取相同层级

思源导入在事务中每插入一篇笔记后调用一次通用的 `synchronizeLegacyNoteHierarchy()`。该通用入口面向单篇增删改，会重新读取笔记、递归读取所属笔记本、确保笔记本节点、读取笔记节点、更新节点并写历史记录。

批量导入时，同一笔记本及其父链会被反复检查。该逻辑保证了导入结果在统一知识树可见，但使用单篇同步入口会产生大量可避免的重复数据库操作。

### 进度由两个状态源重复呈现

`DataManager` 已通过 `importSiyuanPackage(..., onProgress)` 接收后台任务状态，`SiyuanImportProgressBridge` 又通过替换 `window.fetch` 监听同一组 POST/GET 请求并创建第二套进度状态。

桥接卡片每次更新都会递增 `feedback.id`，`AnimatePresence` 因 `key` 变化同时保留退出中的旧卡和进入中的新卡，轮询频率下会周期性出现两张相同卡片并引发布局跳动。

### “解析”是笼统状态

后台任务在领取后只写入一次 `importing` 状态，直到完成或失败才再次更新。其间发生的数据包扫描、文档转换、附件落盘、数据库写入、知识树同步和后处理全部复用同一句文案，无法区分真正卡住的阶段。

## 设计

### 1. 单次打开与单次解析

新增仅供思源导入内部使用的“已准备数据包”结构，包含：

- 已打开 ZIP 的安全条目列表；
- 已解析且完成 ID/路径去重的文档 AST；
- 笔记本配置、排序、自定义图标及保真节点判断结果；
- 元数据扫描产生的警告。

增强包装层完成安全预算检查和元数据读取后，将同一个准备结果沿 `siyuanPackageImportLegacy.ts` 传给核心导入器。核心导入器复用其中的条目、文档索引和笔记本名称：

- 不再次调用 `unzipper.Open.file()`；
- 不再次对 `.sy` 条目调用 `entry.buffer()`；
- 不再次执行 `JSON.parse()`；
- 附件仍从已校验的同一条目集合读取；
- ZIP 条目数、单文档大小、元数据大小和路径安全限制保持不变。

该结构不进入公开 API，不写入数据库，也不出现在后台任务结果中，任务结束后即可被垃圾回收。

### 2. 导入专用的批量知识树同步

在 `legacyKnowledgeHierarchy.ts` 增加仅用于“同一事务内新建一批目录和笔记”的批量同步入口，现有单篇同步函数及普通笔记 API 行为不变。

批量入口执行以下流程：

1. 只初始化一次知识树存储。
2. 对本批次涉及的笔记本去重，并缓存已经确认的父级节点；同一目录链最多递归校验一次。
3. 分批读取新建笔记所需字段，使用确定性的 `note:<id>` 节点 ID 写入或校正节点。
4. 保留 `create` 历史记录和父级同空间校验。
5. 继续执行导入器现有的批量可见性核验；业务笔记、笔记本或知识树节点任一缺失时，整个事务回滚。

批量入口只接受本次事务中新建的资源 ID，不用于移动、删除、恢复或已有资源修复，避免扩大行为范围。

### 3. 后台任务提供真实阶段

思源导入内部增加轻量进度回调，由 `siyuanImportJobs.ts` 持久化到现有任务记录。阶段定义为：

- `scanning`：校验 ZIP 并读取目录、排序和图标元数据；
- `converting`：逐篇转换文档并解析附件引用，显示“当前篇数 / 总篇数”；
- `persisting`：在事务中写入目录、笔记、附件、标签和知识树；
- `finalizing`：执行富文本增强、远程图片处理、元数据排序和最终一致性检查；
- `completed` / `failed`：沿用现有终态。

任务表增加可空的 `progressCurrent` 与 `progressTotal` 字段。已有数据库通过幂等列检查补齐字段，新建数据库直接使用完整结构。进度更新按阶段变化或固定时间窗口节流，避免每篇文档都触发额外高频写盘。

任务状态机仍为 `queued -> running -> completed|failed`。进度阶段不能改变领取、心跳、过期任务处理和 requestId/jobId 幂等规则。

### 4. 单一 UI 状态源

后台导入开始后，由 `DataManager` 的 `onProgress` 作为设置页内唯一的任务进度状态源：

- 任务状态卡固定挂载，只更新标题、说明和进度宽度；
- 已知总数时显示确定进度和数量，未知总数时显示连续但不改变布局的等待动画；
- 状态变化不替换 React `key`，不重复播放进出动画；
- 导入按钮只承担禁用和简短状态提示，不再渲染第二张完整进度卡。

`SiyuanImportProgressBridge` 保留 ZIP 内容识别和文件名规范化职责，但不再替换 `window.fetch` 监听思源后台任务。文件检查完成后，其临时提示按现有时机消失；真正导入开始后不会与 `DataManager` 重复展示。

### 5. 错误与恢复

- 解压预算、非法路径、文档 JSON 解析和附件写入错误继续进入后台任务 `failed` 终态。
- 浏览器刷新或网络短暂中断仍复用持久化的 requestId/jobId 查询同一个任务，不重新 POST。
- 状态查询达到静默超时或总等待上限时继续返回现有可恢复错误。
- 后端进程中断后的 `running` 任务继续按当前 stale 规则失败，不自动从头重跑。
- 批量知识树同步或最终可见性校验失败时，数据库事务整体回滚；已落盘但未提交的附件继续由现有清理路径删除。

## 数据流

1. 前端流式上传思源包并创建唯一后台任务。
2. Worker 原子领取任务，进入 `scanning`。
3. 导入器打开 ZIP 一次，完成安全校验、元数据收集和 `.sy` AST 解析。
4. 核心导入器复用准备结果，进入 `converting`，逐篇转换正文并处理附件。
5. 导入器进入 `persisting`，在单一事务中批量写业务数据和知识树节点并核验可见性。
6. 外层后处理进入 `finalizing`，完成富文本增强、远程图片和排序图标处理。
7. Worker 写入 `completed` 及紧凑结果，前端停止轮询、刷新目标空间。

## 验证

### 后端

- 新增回归测试，使用可计数的 ZIP 条目证明每个 `.sy` 文档只读取、解析一次，核心导入不会重新打开同一数据包。
- 现有思源导入夹具继续覆盖富文本、Markdown、排序、图标、标签、附件、远程图片和安全预算。
- 新增批量知识树测试：关闭历史自动同步触发器后导入多篇同目录笔记，确认目录与笔记节点全部可见、父级正确、无重复节点且失败时整体回滚。
- 新增任务进度测试，确认阶段顺序、计数单调、进度更新不改变任务状态机以及完成/失败后不再写入运行态。
- 使用中等规模合成包对比优化前后的 `.sy` 解压次数和知识树数据库操作次数；测试以次数上限为断言，不使用容易受机器波动影响的毫秒阈值。

### 前端

- 测试后台轮询多次返回相同或不同进度时始终只有一张任务状态卡。
- 测试已知总数显示确定进度，未知总数显示稳定等待态，终态停止动画。
- 测试 `SiyuanImportProgressBridge` 仍能识别普通 `.zip` 中的思源工作区，但不会再接管后台任务 fetch。
- 运行相关 Vitest、后端思源导入测试以及前后端构建。

## 非目标

- 不改变思源富文本与 Markdown 的转换规则。
- 不改变附件去重、存储位置和引用格式。
- 不改变导入任务的重试、幂等和超时策略。
- 不重构其他导入源或普通笔记增删改的知识树同步入口。
